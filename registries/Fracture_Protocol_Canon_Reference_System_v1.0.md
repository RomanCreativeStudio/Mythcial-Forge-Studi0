# THE FRACTURE PROTOCOL
## Canon Reference System
### Version 1.0

**Classification:** Internal — Production/Governance Document
**Status:** Navigation system only. Introduces zero lore, zero new characters, zero new locations, zero new organizations, zero new powers, zero story events. Every fact named below already exists in an official Bible; this document only records *where*.
**Absolute authority:** `bible/Fracture_Protocol_Master_System_Prompt_v1.2.md` — this document is subordinate to it in all cases and carries no canon authority of its own.
**Companion documents:** `README.md` (Studio Wiki — general navigation across all document types), `governance/Fracture_Protocol_Studio_Governance_Manual_v1.1.md` (process jurisdiction), `bible/Fracture_Protocol_Proposal_Vault_v1.0.md` (where an unanswered question goes).
**Relationship to the Studio Wiki:** the Wiki (README.md) is the general-purpose navigation index for every document in the repository — canon, process, and governance alike. This system is narrower and deeper: it is canon-only, organized by *category of fact* (Characters, Disciplines, Artifacts, etc.) rather than by *document type*, and it exists specifically to answer "where is the canon on X" fast enough that nobody is ever tempted to guess. Where the Wiki already maintains a pointer table for a category (Characters, Environments, Props), this system points to that table rather than rebuilding it — see Section 4.

---

### How to use this document

This is not a Bible. It has no lore in it. Every section below is a table of pointers — a name, and the exact place that name is actually defined. If you need to know what something *is*, follow the pointer and read the source. If you follow every pointer available and the answer still isn't there, that is not an invitation to invent one — see Section 9.

Tags: **[LOCKED]** — founder/Creative Director sign-off required to change. **[LIVING SECTION]** — expands automatically as new canon is added elsewhere; the expansion itself doesn't need sign-off, only the underlying canon does.

## 1. Purpose **[LOCKED]**

This document is the master lookup system for canon. Its only job is to let any creator, department, or AI system instantly locate where an official fact lives, across every Bible, without manually searching each one in turn. It exists because a production scaling toward hundreds of episodes cannot afford "which document says what Kael's eyes do" to be a five-minute search each time — it should be a five-second lookup, every time, with a citation precise enough to defend.

This document answers **"where,"** never **"what."** The moment an answer requires restating what a Bible says rather than pointing to it, that content doesn't belong here — it belongs in the Bible itself, or nowhere.

---

## 2. Authority **[LOCKED]**

This document never creates canon. It has no authority to establish, imply, modify, or complete a fact that isn't already fully stated in an official Bible. It only points to where canon already exists.

The Master System Prompt remains supreme over this document in every case, exactly as it does over every other document in this repository (Master System Prompt Section 2, Source of Truth Rule). If this system and a Bible ever appear to disagree about where something is defined, the Bible is correct and this document's pointer is the bug — fix the pointer, never the Bible, and never treat the disagreement as license to decide the fact independently.

This document carries the same restriction every process and navigation document in this repository carries (Studio Governance Manual Section 4, Canon vs. Process vs. Documentation): it is Documentation, not Canon, and it may never contain a story/world fact, only a citation to one.

---

## 3. How To Use **[LOCKED]**

Every canon question, whether asked by a human writer or an AI system, follows the same required workflow before anything is written down as fact:

```
Question
   │
   ▼
Check Canon Reference System (this document, Section 4)
   │
   ▼
Locate Source Bible (the specific document and section the pointer names)
   │
   ▼
Read Source (open the actual Bible section — never trust a pointer as a
              substitute for reading what it points to)
   │
   ▼
Does the answer exist there?
   │
  ┌┴───────────────┐
 Yes                No
  │                  │
  ▼                  ▼
Use it, cited      Log it in the Proposal Vault
per Section 6      (Master System Prompt Section 12,
                    Rule 5) — never invent it, never
                    infer it, never assume a reasonable
                    default counts as canon
```

No step in this chain may be skipped. A pointer in Section 4 is a starting point, not a final answer — the source itself is always the authority, and this document is never cited *instead of* the Bible it points to, only *as a way to find it faster*.

A single canon question often requires following a chain across more than one document. The standard chain, for a character-centered question, runs:

```
Character Page (Studio Wiki §8)
   │
   ▼
World Bible (Character Creation Rules, home Zone, Signal-affinity — §14, §3)
   │
   ▼
Series Bible Episode (specific appearances, growth, relationships — §6–9, §11)
   │
   ▼
Art Bible Character Sheet (visual lock — currently Master System Prompt §4
   for Kael specifically; per-character sheets planned, Studio Wiki §11)
   │
   ▼
Timeline Entry (which episode/season this applies to — Series Bible §11–12)
```

The same chain shape applies to any category: start at this document's Section 4 pointer, follow it to the owning Bible, then follow that Bible's own internal cross-references outward from there. Never skip a link in the chain by assuming what the next document says — every hop is a real, separate confirmation.

Every citation to canon in a script, prompt, asset spec, or proposal uses this format:

Do not invent a year-numbering citation; none exists in canon.

## 7. Search Rules **[LOCKED]**

When an AI system searches for a canon answer, it checks sources in this order and stops at the first one that actually contains the answer:

```
1. Master System Prompt   — absolute canon lock; checked first, always
        ↓
2. World Bible             — universe/world-mechanic facts
        ↓
3. Series Bible            — story, cast, episode-level facts (includes
                             timeline/sequencing — Section 4, Timeline)
        ↓
4. Art Bible                — visual-only facts
        ↓
5. Production Documents     — Production Bible / Production OS, process
                             facts only, never story/world facts
        ↓
6. Proposal Vault           — confirms whether the question is already a
                             known open proposal, not yet canon
```

If the search reaches the end of this list without a source answer, the question is not "unlikely" or "probably fine to assume" — it is **missing**, and Section 9 applies without exception.

---

## 8. Conflict Resolution **[LOCKED]**

If two documents appear to disagree about a canon fact: **never guess. Always defer to the higher authority**, per the Master System Prompt's Source of Truth Rule and the Studio Wiki's Canon Hierarchy (Studio Wiki Section 3) — this system restates neither in full, only the operating instruction: stop, identify which document ranks higher, treat the lower document's content as the bug, and flag it for correction rather than silently picking whichever version is more convenient for the task at hand.

---

## 9. Missing Information **[LOCKED]**

Absent canon **never** equals permission to invent. If a question reaches the end of Section 7's search order with no answer found anywhere, that silence is not a gap to be filled by inference, precedent, "what would make sense," or narrative convenience — it is logged as a Proposal in the Proposal Vault (Master System Prompt Section 12, Rule 5; format: Status/Purpose/Impact/Recommendation) and left there, unresolved, until the founder explicitly approves it through the Founder Override Protocol (Master System Prompt Section 13). Production continues only on the parts of the work that don't depend on the missing answer.

This is the single most important rule in this document. Every other section exists to make the *positive* case (here's where the answer is) fast and reliable; this section exists to make the *negative* case (there is no answer) equally unambiguous.

## 10. Future Expansion **[LIVING SECTION]**

A new Bible, a new Art Bible file, or a new category of canon fact integrates into this system without restructuring it:

1. Add a new row to the relevant category table in Section 4, or a new category subsection if none of the existing ones fit.
2. If an entirely new document type is introduced (a second series' Series Bible, a new registry), it gets a pointer here the same day it's added to the Studio Wiki's own indices (Studio Wiki Section 24, Maintenance Rules) — this document and the Wiki are updated together, not separately.
3. No existing pointer is renumbered or reorganized to make room for a new one — Section 4's categories are additive by design, matching the same principle the Studio Wiki uses for its own index sections (Studio Wiki Section 24).

## 11. Maintenance **[LIVING SECTION]**

- **Versioning:** this document follows the studio-wide `v{major}.{minor}` convention (Production Bible Section 6) — a new category or a Locked-section change is a major bump; an additive pointer within an existing category is a minor bump.
- **Updating references:** when a Bible is renumbered, retitled, or restructured, every pointer in Section 4 that cites it is checked and corrected the same day (Repository Health Guide Section 3, Broken Link Checks) — this document is explicitly in scope for that audit, not exempt from it.
- **Retiring sections:** a category that no longer applies (e.g., a merged organization) is marked retired in place, never deleted, per the Studio Governance Manual's Retirement Policy (Section 18) — consistent with how Production OS's superseded sections were handled (Decision Log `DEC-0001`).
- **Adding new documents:** see Section 10 (Future Expansion) — the same day a new Bible or Art Bible file is created, it receives a pointer here and in the Studio Wiki.

## 12. Final Validation

1. **No canon added.** Every named entity in this document (Kael, the Authority System, Ward Division, Cipher-work, Root Artifacts, the four megacity layers, etc.) already exists in the Master System Prompt, World Bible, Series Bible, or Art Bible — none was introduced here. Verified by direct grep against every existing canon term before publishing this document: every hit traces to a pre-existing citation, not a new claim.
2. **No lore created.** No section states what anything *is* — every section states only *where* it's defined. Categories that already have a full pointer table elsewhere (Characters at Studio Wiki §8, Locations at Studio Wiki §9, the Terminology Reference at World Bible §13, the Season One episode outline at Series Bible §11) are referenced, not rebuilt, so the same fact is never asserted in two places.
3. **Index only.** This document contains zero character descriptions, zero location descriptions, zero organizational goals or methods, zero power mechanics beyond naming which discipline exists and where it's defined, and zero story events beyond naming which episode/section covers them.
4. **The one deliberate adaptation from the requested template:** the requested citation example "Timeline Year 02" was not implemented literally, because this franchise has no in-world year-numbering system (World Bible Section 2 deliberately withholds a dated history, and Studio Wiki Section 17 explicitly bars reintroducing one without founder sign-off). Section 6 explains the substitution (season/episode citation instead) rather than silently inventing a timeline convention that would itself have been new canon.
5. **Compatible with all existing documents** — checked against Studio Wiki Sections 8–13, 15–17, 19; World Bible Sections 2–4, 6–9, 11, 13–16; Master System Prompt Sections 3–6, 12–13; Production Bible and Production OS's current (post-Decision-Log-`DEC-0001`) scope split. No contradictions found.
